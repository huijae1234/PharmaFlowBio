## 지표 정의: 평균 처리 일수 (관리자 대시보드, spec 002 FR-010)
| 항목 | 정의 |
|---|---|
| 뜻 | 품질 이슈를 연 뒤 닫을 때까지 평균 며칠 걸렸는가 |
| 분자 | 닫힌 이슈마다 (닫은 시각 − 연 시각)을 일수로 바꾼 값의 합 |
| **분모** | **닫힌 이슈의 수** (상태가 닫힘이고 닫은 시각이 있는 것만). 열린 이슈는 분모에도 분자에도 넣지 않는다 |
| 닫힌 이슈가 0건 | 평균은 "없음"(0이 아님) |
| 표시 | 소수 첫째 자리 반올림 |
| 계산 위치 | `src/domain/dashboard-rules.js`의 `issueKpis` |
| 함께 보이는 숫자 | 열린 품질 이슈 수 = 상태가 열림인 이슈 수(분모 없음, 건수). **화면 글자는 "처리 중 품질 이슈"**(`src/ui/pages/homes.js`)이고 같은 값이다 |

분모를 "전체 이슈"로 잡으면 아직 열려 있는 이슈의 처리 시간이 정해지지 않아 평균이 거짓으로 낮아진다. 그래서 닫힌 것만 센다.

## 손으로 센 값 (예시 자료 기준, 2026-10-29)
기준 자료는 `supabase/migrations/0018_bio_samples.sql`의 가상 예시 이슈 4건이다(시각은 기준 시각 t0에서 뺀 값).

| 이슈 | 상태 | 연 시각 | 닫은 시각 |
|---|---|---|---|
| HBV-2610-001 역가 규격 이탈 | 열림 | t0 − 4일 4시간 | — |
| HBV-2610-002 엔도톡신 관리기준 이탈 | 열림 | t0 − 7일 4시간 | — |
| HBV-2610-003 알루미늄 함량 규격 이탈 | 닫힘 | t0 − 12일 4시간 | t0 − 8일 6시간 |
| TDP-2610-001 보관 온도 공정 이탈 | 열림 | t0 − 2시간 20분 | — |

| 숫자 | 손으로 센 값 | 함수 계산 | 맞음? |
|---|---|---|---|
| 열린 이슈 수 | 3건 (표에서 "열림" 세 줄) | 3 | 맞음 |
| 분모(닫힌 이슈) | 1건 | 1 | 맞음 |
| 평균 처리 일수 | 12일 4시간 → 8일 6시간 = 3일 22시간 = 3 + 22/24 = 3.917일 → **3.9일** | 3.9 | 맞음 |
| 닫힌 이슈 1건 더 추가(10일 전에 열어 8일 전에 닫음 = 2일) | (3.917 + 2) / 2 = 2.96 → **3.0일** | 3 | 맞음 |
| 닫힌 이슈 0건 | 없음 | null(없음) | 맞음 |

함수 계산은 같은 값을 `issueKpis`에 넣어 `node`로 직접 돌려 얻었다. 코드 시험은 `tests/dashboard-rules.test.js`.

## 실제 화면 숫자를 손으로 세어 맞추는 법 (점검표 18번, 2026-10-29 윤○○ 확인 완료)
관리자 대시보드의 두 숫자를 **품질 이슈 목록**으로 직접 센 값과 비교한다. 2026-10-29 캡처([qa-admin-dashboard.png](../assets/captures/18-numbers/qa-admin-dashboard.png))에는 "처리 중 품질 이슈 5건", "평균 처리 2.0일"이 보인다. 이 값은 위 예시(3건·3.9일)와 다르다.
1. 대시보드를 캡처한 **바로 그 시각**에 `#/issues`를 연다(이슈 목록은 모든 역할이 볼 수 있다).
2. 상태가 "처리 중"인 이슈를 센다 → 대시보드 "처리 중 품질 이슈"와 같아야 한다(같은 값: 상태 열림, `issueKpis`의 `openCount`).
3. 상태가 "종결"인 이슈마다 이슈 상세에서 **연 시각과 닫은 시각**을 읽어 (닫은 − 연)을 일수로 계산하고, 그 평균(소수 첫째 자리 반올림)을 낸다 → 대시보드 "평균 처리"와 같아야 한다. 분모는 종결 이슈 수다.
4. 아래 표를 채운다. 다르면 이슈를 더 만들었는지(캡처 이후 변동), 시간대 차이를 먼저 의심한다.

| 숫자 | 대시보드 | 직접 센 값 | 센 사람·시각 | 맞음? |
|---|---|---|---|---|
| 처리 중 품질 이슈 | 5건 (캡처 시각 13:24) | 이슈 목록과 대조 | 윤○○, 2026-10-29 | 맞음(이상 없음) |
| 평균 처리(종결 이슈만) | 2.0일 | 이슈 목록과 대조 | 윤○○, 2026-10-29 | 맞음(이상 없음) |

같은 대시보드를 **14:52**에 휴대폰으로 찍은 캡처([qa-dashboard-phone.png](../assets/captures/22-mobile/qa-dashboard-phone.png))에는 처리 중 품질 이슈 **4건**, 평균 처리 **1.9일**이 보인다. 13:24의 5건·2.0일에서 88분 사이에 바뀐 것이다(이슈 한 건이 종결됐을 가능성이 있으나 확인하지 못함). 그래서 위 표는 **캡처 시각과 같은 시각의 목록**으로 세어야 한다. 윤○○의 확인은 김희재가 "이상 없음"으로 전달했고, 센 숫자와 대조한 시각은 기록으로 받지 못했다.

## 확인하지 못한 것
- **실제 화면의 숫자와 맞춰 보지 않았다.** 위 표는 예시 자료와 함수 계산을 손으로 맞춘 것이다. 팀원이 로그인해 관리자 대시보드의 "열린 품질 이슈 수"·"평균 처리 일수"를 보고, 실제 DB의 이슈 수와 같은지 확인해야 한다(팀 DB는 이 환경에서 읽지 못했다).
- 실제 DB는 사용자가 이슈를 더 만들었을 수 있어 숫자가 위 값과 다를 수 있다. 그때는 이슈 목록에서 열림·닫힘을 세어 비교한다.
- 이번 주 기준 이탈 수는 "이번 주"를 월요일 0시(브라우저 시간)로 임시 처리한 값(Q22)이라 이 문서의 분모 검증 대상이 아니다.
