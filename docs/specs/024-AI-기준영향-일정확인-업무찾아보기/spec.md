## 1. 바뀌는 것
- **새로 생기는 것:** 서버 `api/ai.js`에 종류 3개(`spec_impact`·`schedule_check`·`ask`), 규칙 파일 3개(`ai-spec-impact-rules`·`ai-schedule-rules`·`ai-ask-rules`), 서버 읽기·풀이 모듈(`api/_ai-ask.js`), 화면 칸 3개(제품 상세·작업지시·각 역할 홈).
- **기존 화면에 닿는 곳(모두 칸을 지우면 이전과 같다):** 제품 상세 기준 표 아래, 작업지시 목록 위, 세 홈의 "지금 할 일" 아래. DB·표·권한·판정·알림은 바꾸지 않았다. 새 라이브러리 없음.
- **기존 GMP×작업지시 대조를 다시 만들지 않는다:** 일정 확인은 공개 규제 정보를 계산하지 않고 제품 상세 "규제" 탭의 기존 확인 목록을 안내한다(같은 경고 카드를 중복 생성하지 않음). 공개 규제 정보를 이 확인에 **함께 참조하지는 못했다**(5-2절 한계).

## 2. 기능 4 — 기준 변경 영향 설명 (FR-057)
**위치:** QA의 제품 상세(기준 관리) 기준 표 아래 "AI로 기준 변경 영향 설명"(접어 둠). 항목 하나를 고른다. **누가:** QA만(서버 확인).
**코드가 계산한다:** 그 항목의 측정값마다 저장된 **판정 당시 기준·버전**(`applied_*`)과 **현재 기준**으로 같은 값을 다시 판정해 센다.

| 분류 | 처리 |
|---|---|
| 현재와 같은 버전 | 기준이 같으므로 비교하지 않음(건수만) |
| 다른 버전, 판정이 같음 | 유지 |
| 다른 버전, 판정이 달라짐 | 변경(최대 5건의 로트·값·당시 판정 → 현재 기준 판정) |
| 판정 당시 기준이 저장돼 있지 않음 | **비교 불가**(임의로 채우지 않음) |
| 단위가 다름(측정 당시 단위가 있을 때) | **비교 불가**. 현재 스키마에는 측정 당시 단위가 저장되지 않아 이 건수는 늘 0이고, 근거 표에 "측정 당시 단위는 저장되지 않아 단위 차이를 확인할 수 없음"을 줄로 둔다 |
| 조회 실패·300건 상한 | 비교하지 않음(`failed`: 없음으로 말하지 않음) |

판정 규칙은 DB `private.judge`와 같다(규격 경계는 안쪽, 관리기준이 있고 밖이면 관리기준 이탈). **저장돼 있지 않은 과거 기준은 복원했다고 주장하지 않는다**(버전이 같으면 같은 기준일 뿐). 비교한 측정이 하나라도 있을 때만 AI를 부른다.
**AI가 하는 일:** "측정값이 달라진 것이 아니라 기준이 달라져 비교 판정이 달라지는 것"을 구분하고 확인할 항목(비교 불가 건수 등)을 설명한다. 결과마다 **"현재 기준으로 비교한 참고 결과"** 안내를 먼저 보인다. **하지 않는 일:** 원래 판정·로트 상태·승인 이력 변경, 기준 수정, 소급 판정, 출하 승인 지시(금지 표현 검사 `retro`·`restore`).
**수용 기준:** (1) 판정 변경·유지·기준 누락·단위 차이가 시험으로 갈린다. (2) 안내 문구와 한계 줄이 항상 보인다. (3) 비교 불가·조회 실패는 "변경 없음"으로 말하지 않는다. (4) 서버가 기준 ID로 읽고 QA가 아니면 403.

## 3. 기능 5 — 생산 일정에 영향을 주는 미완료 업무 확인 (FR-058)
**위치:** 작업지시 목록 위 "AI로 일정에 영향을 주는 미완료 업무 확인"(접어 둠). **누가:** 생산(자기 차례 중심)·QA(전체 검토). QC·열람자는 금지.
**코드가 계산한다(한국 날짜 기준):** 진행 전·진행 중(초안·발행·진행 중) 작업지시마다 — 계획 종료일이 지났나(오늘은 아직 아님), 시작일이 지났는데 착수 전인가, 7일 안에 시작하는데 아직 발행·착수 전인가, 연결된 로트가 보류인가, 그 로트의 열린 이슈마다 **다음 행동과 맡을 역할**(평가서 작성 → QA 검토 → 보완 → 조치 승인 → 결과 입력 → 종결), 진행 중인 공정 단계. 신호가 있는 작업지시만 최대 8건, 종료일 지남·내 차례 순으로 근거 표에 둔다. 역할이 맞는 다음 행동은 `[내 차례]`로 먼저 보인다.
**AI가 하는 일:** 확인 순서·담당 역할·근거 줄·이동 링크를 문장으로 정리한다(이동 링크는 서버가 준다: 이슈·로트·작업지시 목록). **하지 않는 일:** 소요시간·설비·인력 자료가 없으므로 **완료일·지연일 예측, 최적 일정·배정 제외**(금지 표현 검사 `predict`·`reassign`), 계획일·담당자 변경, 알림 자동 실행.
**수용 기준:** (1) 날짜 경계(종료일이 오늘/어제, 시작일 7일 경계)·보류·미완료 업무가 시험으로 갈린다. (2) 이슈·평가·조치 상태를 읽지 못하면 "보류 이유를 알 수 없음"을 `못 읽음` 줄로 남긴다. (3) 신호가 없거나 작업지시를 읽지 못하면 AI를 부르지 않고 "문제없다는 뜻은 아니다"라고 쓴다. (4) 작업지시를 500건까지만 읽고 넘으면 비교하지 않는다.
**5-2 한계:** GMP 유효기간 등 공개 규제 정보는 일정 확인 근거에 넣지 못했다(제품별 공개 API 호출이 필요해 이 한 번의 호출에 싣지 않음). 제품 상세 규제 탭의 기존 카드가 하는 일은 그대로이고 여기서는 안내만 한다.

## 4. 기능 6 — 범위를 제한한 업무 질문 "업무 찾아보기" (FR-059) — **삭제됨**
> **2026-10-29 사용자 결정: 업무 찾아보기는 만들지 않는다.** 홈의 질문칸을 뺐다. AI 도우미(spec 025)에도 넣지 않는다. 아래는 기록으로만 남긴다. 서버 쪽 조회 코드(`api/_ai-ask.js`·`src/domain/ai-ask-rules.js`·`src/ui/ask-box.js`와 시험)는 화면에서 부르지 않으며, 지울지는 사용자 확인 뒤.
**위치:** QA·QC·생산 홈의 "지금 할 일" 아래 작은 칸(접어 둠). 별도 챗봇이 아니다. 입력칸과 그 역할이 실행할 수 있는 예시 질문 버튼을 둔다.
**조회 종류 4개(그 밖의 질문은 실행하지 않는다):**

| 종류 | 설명 | 허용 필터 | 역할 |
|---|---|---|---|
| `held_lots` | 보류 로트 | `olderThanDays`(1~365) | QA·QC·생산 |
| `pending_reviews` | 평가 검토 대기 | `olderThanDays` | QA |
| `my_actions` | 나에게 배정된 미완료 조치 | `actionType`(4종) | QA·QC·생산 |
| `overdue_orders` | 계획 종료일이 지난 미완료 작업지시 | `overdueDays`(1~365) | QA·생산 |

**동작:** 예시 버튼·고른 후보는 **AI를 부르지 않고** 바로 조회한다. 자유 질문(120자 이내)만 Claude가 "종류와 허용 필터로 해석"하고, 서버가 종류·필터·역할을 **다시 검사**한 뒤 준비된 읽기 함수로 조회한다(질문 글은 따옴표 안의 자료로만 보내고, 해석 결과의 종류는 정해진 6가지 말(4종·ambiguous·unsupported)만 받는다). 결과는 실제 **목록·개수·조회 조건·조회 시각·화면 링크**로 보이고, 읽기 상한(200건)과 표시 상한(30건)을 넘으면 알린다. 모호하면 후보를 고르게 하고(역할에 맞는 후보만), 범위 밖이면 가능한 질문을 안내한다.
**신뢰 경계:** 질문에 적힌 사용자·역할은 권한이 아니다. 역할은 서버가 DB에서 읽고, "내 업무"는 **로그인한 사용자로 서버가 정한다**(필터에 사용자·역할이 없고, 있으면 400). 역할에 맞지 않는 종류는 해석이 맞아도 403이고 조회하지 않는다. 임의 SQL·코드·URL 실행, 관리자 권한 우회, 수정·승인·전송 없음(시험으로 확인).
**수용 기준:** (1) 4종 질문이 역할별로 실행/거부된다. (2) 모호함·범위 밖·악성 지시("SQL 실행", "이전 지시 무시")는 조회하지 않는다. (3) 위조한 필터·사용자·범위 밖 값은 400. (4) 해석에 닿지 못하면 한도를 돌려준다.

## 5. 공통
- **버튼을 눌렀을 때만 호출**, 중복·연속 클릭·동시 호출 제한, 하루 한도(spec 022와 같은 풀: 자유 질문 해석과 AI 설명만 센다, 예시 조회는 세지 않음), 길이·시간 제한은 spec 022·023과 같다.

## 6. 열린 질문과 한계
- **실제 Claude 응답을 보지 못했다.** 특히 질문 해석 JSON이 우리 6가지 말을 지키는지, 설명 문장이 금지 표현 검사에 과하게 막히는지는 키를 넣은 뒤 확인해야 한다(qa.md 4절).
- 기준 변경 영향은 측정 당시 단위가 저장되지 않아 단위 차이를 실제로 가려내지 못한다(스키마 한계, 설계상 "비교 불가" 규칙은 구현·시험됨).
- 일정 확인은 규제 정보를 참조하지 못했고, 날짜·미완료 업무만 본다. 열린 이슈가 있는 로트가 100개를 넘으면 일부만 읽은 것으로 표시한다(`못 읽음`).
- 업무 찾아보기의 키워드 해석은 시험 모드(가짜)에서 쓴 단순 규칙이고, 실제 해석 품질은 미확인이다.
- 질문에 쓴 이름·역할은 무시되므로 "김희재 님 조치" 같은 질문은 로그인한 사람의 조치를 보여 준다(그렇게 해석되었음을 "이렇게 이해했습니다"로 알린다).
