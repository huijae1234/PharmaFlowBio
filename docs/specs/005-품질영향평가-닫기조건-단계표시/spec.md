## 1. 해결하려는 문제
**지금 방식:** 이탈이 생기면 품질 이슈가 열리고 조치 요청 → 승인 → 결과 → 이슈 닫기로 처리된다. 이탈 원인과 품질 영향은 앱 밖(워드 평가서·메일)에 있고, 완료된 조치가 하나만 있으면 재시험이 또 이탈이어도 이슈를 닫을 수 있다. 관리기준 이탈 이슈는 조치를 꼭 해야 하는지 정해지지 않았다. 지금 어느 단계이고 누가 무엇을 해야 하는지는 화면을 여기저기 봐야 안다. [코드 기능 002·004] [UJ CUJ-01 3·4단계 As-Is]
**막히는 지점:**
- 영향 평가서를 옮겨 적고 메일로 주고받아 근거가 흩어진다. 평가 승인과 출하 승인이 섞여 "특채"로 오해될 수 있다. [UJ CUJ-01 4단계 pain] [UJ 에러 E8]
- 이슈를 닫을 근거(승인된 평가)가 없어도 닫힌다. [PRD FR-32] [전환 D8]
- 이슈·로트의 지금 단계와 다음에 할 일이 한눈에 보이지 않아 1분 안 내부 출하 검토가 어렵다. [문제정의 v2 확인할 것 하나] [PRD FR-36]

## 2. 주요 사용자
**사용자:** QC 시험 담당자·생산 담당자(영향 평가 작성·다시 제출), QA 관리자(영향 평가 검토, 이슈 닫기, 내부 출하 검토). [PRD §4] [ERD 권한 요약 deviation_review]

### 이야기 1 — 담당자가 영향 평가를 써서 QA 검토를 요청한다 (P1)
- 장면: QC 시험 담당자가 품질 이슈 상세에서 "품질 영향 평가 작성"을 열면 로트·발생 일시·시험 항목·측정값·적용 기준과 버전이 이미 보인다. 이탈 내용·추정 원인·품질 영향·제안 후속 조치·근거를 적어 검토를 요청한다. [UJ CUJ-01 3단계] [PRD FR-30] [IA QI_010105_MD]
- 왜 P1: CUJ-01의 새 단계이고, 닫기 조건(이야기 3)의 전제다.
- 혼자 확인하는 방법: VX-2610-004의 관리기준 이탈 이슈에서 평가를 작성 → 상태 "검토 요청"과 업무 이력이 보인다.

### 이야기 2 — QA 관리자가 영향 평가를 승인·반려·보완 요청한다 (P1)
- 장면: QA 관리자가 승인 대기에서 영향 평가를 열어 승인하거나, 사유를 적어 반려·보완 요청한다. 승인 창에는 "사용·출하 승인이 아닙니다"가 보인다. 보완 요청을 받은 요청자는 같은 평가를 고쳐 다시 제출한다. [UJ CUJ-01 4단계] [UJ 에러 E7] [PRD FR-31] [IA QI_010106_MD, AD_010000_PG]
- 왜 P1: 근거를 남긴 승인 이력이 문제정의의 핵심이다.
- 혼자 확인하는 방법: 보완 요청(사유) → 요청자 첫 화면에 보임 → 고쳐 다시 제출 → 승인.

### 이야기 3 — 이슈는 종류에 맞는 조건을 채워야 닫힌다 (P1)
- 장면: 규격 이탈 이슈는 승인된 영향 평가와 완료된 조치가 있어야, 관리기준 이탈 이슈는 승인된 영향 평가가 있어야 닫힌다. 못 닫으면 이유가 글로 보인다. 영향 평가 승인만으로 출하되지 않는다. [PRD FR-32, FR-33] [UJ CUJ-01 5·6단계] [UJ 에러 E8] [전환 D8]
- 왜 P1: Phase 4 완료 기준이고, "특채 금지"를 지키는 규칙이다. [전환 §8 Phase 4]
- 혼자 확인하는 방법: 평가 없이 닫기 → 이유 표시, 평가 승인 뒤 → 닫힘(관리기준 이탈) 또는 조치 완료 뒤 닫힘(규격 이탈).

### 이야기 4 — 지금 단계와 다음에 할 일을 한눈에 본다 (P2)
- 장면: 품질 이슈 상세 위쪽 단계 표시줄(이탈 → 영향 평가 → 조치 → 이슈 종료 → 내부 출하 검토)에서 지금 단계와 다음에 할 일·담당이 보이고, 로트 상세 위쪽 요약에 종류별 열린 이슈 수·영향 평가 상태·다음에 할 일이 보인다. [PRD FR-36] [IA QI_010100_PG, BT_010200_PG 콘텐츠 우선순위]
- 왜 P2: 흐름은 이야기 1~3만으로 끝까지 되고, 이것은 빨리 보게 하는 것이다. 다만 발표의 "1분 안" 장면에 쓰인다.
- 혼자 확인하는 방법: 같은 이슈를 단계마다 열어 표시줄 강조 위치와 다음에 할 일이 바뀌는지 본다.

### 이야기 5 — 첫 화면과 승인 대기에 영향 평가가 보인다 (P2)
- 장면: QA 관리자 대시보드·승인 대기에 검토를 기다리는 영향 평가가 조치 요청과 함께 보이고, 담당자 첫 화면 "보완 요청·반려된 내 요청"에 자기 평가가 보인다. [PRD FR-04, FR-31] [IA HM_010000~030000_PG, AD_010000_PG]
- 혼자 확인하는 방법: 검토 요청 뒤 대시보드 승인 대기 수가 1 늘고, 보완 요청 뒤 요청자 첫 화면에 그 평가가 보인다.

## 3. 핵심 기능과 요구사항

### FR-001 품질 영향 평가 작성·검토 요청 (P1, QI_010100_PG, QI_010105_MD)
QC 시험 담당자·생산 담당자·QA 관리자가 열린 품질 이슈에 영향 평가를 제출할 때, 시스템은 필수 칸을 확인하고 이슈당 하나의 평가를 "검토 요청" 상태로 저장해야 한다. [PRD FR-30] [ERD deviation_review] [전환 D7]
- 수용 기준
  1. **전제** 평가가 없는 열린 이슈 **행동** "품질 영향 평가 작성"을 연다 **결과** 로트번호·발생 일시·시험 항목·측정값·판정·적용 기준과 버전이 자동으로 보인다(공정 이슈면 공정 기록과 설비 상태) (Q33)
  2. **전제** 같은 창 **행동** 이탈 내용·추정 원인·품질 영향 평가·제안 후속 조치 중 하나라도 비우고 제출 **결과** 저장되지 않고 빈 칸 옆에 "○○을 입력해 주세요."가 보인다. 근거는 비워도 된다
  3. **전제** 같은 창 **행동** 모두 채워 제출 **결과** 이슈 상세 품질 영향 평가 칸에 내용·상태 "검토 요청"·요청자·시각이 보이고 업무 이력에 "품질 영향 평가 검토 요청"이 남는다
  4. **전제** 이미 평가가 있는 이슈 **행동** 다시 작성하려 함 **결과** 작성 버튼이 없고, 데이터베이스도 두 번째 평가를 거부한다
  5. **전제** 열람자, 닫힌 이슈, 내부 출하 검토가 끝난 로트 **행동** 작성 시도 **결과** 버튼이 없고 데이터베이스도 거부한다

### FR-002 QA 관리자의 승인·반려·보완 요청 (P1, QI_010106_MD, AD_010000_PG)
QA 관리자가 "검토 요청" 상태의 평가를 검토할 때, 시스템은 승인·반려·보완 요청 중 하나를 저장하고, 반려·보완 요청에는 사유를 받아야 한다. [PRD FR-31] [ERD deviation_review.status·review_comment] [GLOSSARY 보완 요청·반려]
- 수용 기준
  1. **전제** 검토 요청 평가 **행동** 검토 창을 연다 **결과** 평가 내용과 이탈 근거가 보이고, "승인은 영향 평가를 받아들인다는 뜻이며 사용·출하 승인이 아닙니다." 안내가 보인다
  2. **전제** 같은 창 **행동** 반려 또는 보완 요청을 사유 없이 저장 **결과** 저장되지 않고 "사유를 입력해 주세요."
  3. **전제** 같은 창 **행동** 승인 / 반려(사유) / 보완 요청(사유) **결과** 상태가 "승인" / "반려" / "보완 요청"으로 바뀌고 검토자·시각·사유가 보이며 업무 이력에 남는다
  4. **전제** QA 관리자가 아닌 역할 **행동** 검토 시도 **결과** 버튼이 없고 데이터베이스도 거부한다
  5. **전제** 두 QA 관리자가 같은 평가를 동시에 처리 **행동** 나중 사람이 저장 **결과** "다른 사람이 먼저 처리했습니다. 화면을 새로 고칩니다."와 최신 상태 (기존 FR-25와 같은 방식)
  6. **전제** 승인된 평가 **행동** 다시 검토·수정 시도 **결과** 버튼이 없고 데이터베이스도 거부한다 (승인은 최종)

### FR-003 보완 요청·반려 뒤 다시 제출 (P1, QI_010105_MD)
평가가 보완 요청 또는 반려 상태일 때, 시스템은 그 평가의 요청자에게만 같은 평가를 고쳐 다시 제출하게 해야 한다. [PRD FR-31] [ERD deviation_review "반려·보완 요청 → 다시 제출"] [UJ 에러 E7]
- 수용 기준
  1. **전제** 보완 요청된 평가 **행동** 요청자가 이슈 상세를 연다 **결과** "보완 요청 — 사유: …"와 "고쳐 다시 제출" 버튼, 창에는 지난 내용이 채워져 있다
  2. **전제** 같은 창 **행동** 고쳐 제출 **결과** 상태가 "검토 요청"으로 돌아가고 검토 사유는 지워지며(지난 사유는 업무 이력에 남음) 업무 이력에 "품질 영향 평가 다시 제출"
  3. **전제** 요청자가 아닌 사람 **행동** 다시 제출 시도 **결과** 버튼이 없고 데이터베이스도 거부한다
  4. **전제** 반려된 평가 **행동** 요청자가 연다 **결과** "반려 — 사유: …"와 같은 "고쳐 다시 제출" 버튼

### FR-004 이슈 종류별 닫기 조건 (P1, QI_010100_PG)
품질 이슈를 닫을 때, 시스템은 이슈 종류에 맞는 조건을 확인하고 못 닫으면 이유를 보여 줘야 한다. [PRD FR-32] [ERD quality_issue 닫기 조건] [전환 D8]
- 조건: 공통 — 승인된 영향 평가가 있고, 승인 대기·승인됨 조치 요청이 없다. 규격 이탈 — 여기에 완료된 조치 요청 1건 이상. 닫는 사람 — 그 이슈의 조치 요청에 배정됐던 사람 또는 QA 관리자(Q19 그대로).
- 수용 기준
  1. **전제** 영향 평가가 없거나 승인되지 않은 이슈 **행동** 닫기 **결과** 닫히지 않고 "승인된 품질 영향 평가가 없어 닫을 수 없습니다."(화면·데이터베이스)
  2. **전제** 승인된 평가 + 열린 조치 요청 **행동** 닫기 **결과** "끝나지 않은 조치 요청이 있어 닫을 수 없습니다." (지금과 같음)
  3. **전제** 규격 이탈 이슈, 승인된 평가, 완료된 조치 없음 **행동** 닫기 **결과** "완료된 조치 요청이 없어 닫을 수 없습니다. 먼저 조치 결과를 넣어 주세요."
  4. **전제** 관리기준 이탈 이슈, 승인된 평가, 조치 없음 **행동** QA 관리자가 닫기 **결과** 닫힌다
  5. **전제** 규격 이탈 이슈, 승인된 평가, 완료된 조치 **행동** 닫기 **결과** 닫히고, 마지막 열린 규격 이탈 이슈이며 직접 보류가 아니면 로트가 보류 → 시험 중 (지금과 같음)

### FR-005 영향 평가 승인은 출하 승인이 아니다 (P1, BT_010208_MD)
영향 평가가 승인됐어도, 시스템은 내부 출하 검토의 출하 가능 조건(열린 이슈 없음, 시험 항목 마지막 값이 규격 안)을 그대로 적용해야 한다. [PRD FR-33] [UJ 에러 E8] [spec 004 FR-008]
- 수용 기준
  1. **전제** 규격 이탈 이슈의 평가 승인, 조치 미완료 **행동** 출하 가능 **결과** "열린 품질 이슈가 1건 있어 출하할 수 없습니다."로 막힘(화면·데이터베이스)
  2. **전제** 이슈를 닫았지만 마지막 측정값이 규격 이탈 **행동** 출하 가능 **결과** "시험이 끝나지 않은 항목이 있습니다: …"로 막힘
  3. **전제** 영향 평가 승인 창·이슈 상세 **행동** 본다 **결과** "사용·출하 승인이 아닙니다" 문구가 있다

### FR-006 단계 표시줄과 다음에 할 일 (P2, QI_010100_PG)
품질 이슈 상세를 열 때, 시스템은 단계 표시줄(이탈 → 영향 평가 → 조치 → 이슈 종료 → 내부 출하 검토)에 지금 단계를 강조하고 다음에 할 일과 담당 역할을 보여야 한다. [PRD FR-36] [IA QI_010100_PG 콘텐츠 우선순위 1]
- 다음에 할 일 규칙(위에서부터 먼저 맞는 것):
  1. 이슈 닫힘 + 로트가 내부 출하 검토 대기(시험 중, 열린 이슈 없음) → "내부 출하 검토" · QA 관리자
  2. 이슈 닫힘 → "이슈 종료됨" (그 밖의 로트 상태는 로트 상세에서)
  3. 평가 없음 → "품질 영향 평가 작성" · QC 시험 담당자·생산 담당자
  4. 평가 보완 요청·반려 → "평가 고쳐 다시 제출" · 요청자 이름
  5. 평가 검토 요청 → "영향 평가 검토" · QA 관리자
  6. 승인 대기 조치 요청 있음 → "조치 요청 승인" · QA 관리자
  7. 승인된 조치 요청 있음 → "조치 결과 입력" · 배정된 담당자 이름
  8. 규격 이탈 + 완료된 조치 없음 → "조치 요청 등록" · QC 시험 담당자·생산 담당자
  9. 나머지 → "이슈 닫기" · 배정됐던 담당자 또는 QA 관리자
- 수용 기준
  1. **전제** 위 규칙의 각 상태 **행동** 이슈 상세를 연다 **결과** 표시줄 강조 단계와 다음에 할 일·담당이 규칙대로 (함수 시험으로 9가지 모두)
  2. **전제** 관리기준 이탈 이슈 **행동** 연다 **결과** "조치" 단계에 "(선택)"이 붙는다
  3. **전제** 휴대폰 폭 375px **행동** 연다 **결과** 표시줄이 줄을 바꿔 가로 스크롤이 생기지 않고, 지금 단계는 색만이 아니라 글자("지금")로도 표시된다

### FR-007 로트 상세 위쪽 요약 (P2, BT_010200_PG)
로트 상세를 열 때, 시스템은 위쪽에 열린 품질 이슈 수(규격 이탈 N·관리기준 이탈 N), 영향 평가 상태별 수, 다음에 할 일을 보여야 한다. [PRD FR-36] [IA BT_010200_PG 콘텐츠 우선순위 2]
- 수용 기준
  1. **전제** VX-2610-004처럼 관리기준 이탈 이슈 1건(평가 없음) **행동** 로트 상세 **결과** "열린 품질 이슈: 규격 이탈 0 · 관리기준 이탈 1", "영향 평가: 작성 전 1", 다음에 할 일 "품질 영향 평가 작성"
  2. **전제** 열린 이슈 0, 시험 중 **행동** 로트 상세 **결과** 다음에 할 일 "내부 출하 검토" (QA 관리자)
  3. **전제** 열린 이슈가 여럿 **행동** 로트 상세 **결과** 다음에 할 일은 가장 오래된 열린 이슈의 것 + "외 N건"

### FR-008 첫 화면·승인 대기에 영향 평가 (P2, HM_010000_PG, HM_020000_PG, HM_030000_PG, AD_010000_PG)
시스템은 검토 요청 상태의 영향 평가를 QA 관리자 대시보드와 승인 대기에, 보완 요청·반려된 평가를 요청자의 첫 화면에 보여야 한다. [PRD FR-04, FR-31] [IA HM_010000_PG, AD_010000_PG]
- 수용 기준
  1. **전제** 검토 요청 평가 1건 **행동** QA 관리자 대시보드·승인 대기 **결과** 승인 대기 수에 포함되고 목록에 "품질 영향 평가 · 로트번호 · 요청자 · 요청 시각"이 오래된 순으로, 누르면 그 이슈 상세
  2. **전제** 요청자의 평가가 보완 요청·반려 **행동** 요청자 첫 화면 **결과** "보완 요청·반려된 내 요청"에 평가가 사유와 함께 보인다
  3. **전제** 대기·되돌아온 평가 없음 **행동** 같은 화면 **결과** 지금과 같은 빈 안내

### 경계·예외 상황
- 공백만 넣은 필수 칸: 빈 칸으로 본다. 각 칸 1,000자까지, 넘으면 저장 거부와 이유. (FR-001·003)
- 같은 이슈에 두 사람이 동시에 첫 평가 제출: 하나만 저장되고 나중 사람은 "이미 품질 영향 평가가 있습니다. 화면을 새로 고칩니다." (FR-001)
- 검토 요청 중인 평가를 요청자가 고치려 함: 고칠 수 없다(검토가 끝날 때까지). (Q34) (FR-003)
- 승인 뒤 재시험이 규격 이탈로 나와 이슈 종류가 관리기준 → 규격 이탈로 바뀜: 평가 승인은 그대로, 대신 규격 이탈 닫기 조건(완료된 조치)이 적용된다. (Q35) (FR-004)
- 이 기능 전부터 열려 있던 이슈(평가 없음): 평가를 작성·승인해야 닫힌다. 이미 닫힌 이슈는 그대로. (FR-004)
- 관리기준 이탈 이슈에 조치 요청이 있으면: 그 조치가 끝나야(승인 대기·승인됨 없음) 닫힌다. (FR-004)
- 이슈가 닫힌 뒤나 로트 내부 출하 검토 뒤: 평가 작성·검토·다시 제출 모두 불가. (FR-001~003)
- 저장 실패: 입력값을 지키고 평가·이력이 반쯤 생기지 않는다 (기존 FR-17). (FR-001~003)

### 핵심 자료
- **품질 영향 평가**: 품질 이슈 하나에 하나. 갖는 정보: 이탈 내용, 추정 원인, 품질 영향 평가, 제안 후속 조치, 근거(선택), 상태(검토 요청·승인·반려·보완 요청), 요청자·마지막 제출 시각, 검토자·검토 시각·사유. 로트·측정값·기준은 이슈에서 읽어 따로 저장하지 않는다. [ERD deviation_review]
- **품질 이슈**: 닫기 조건에 영향 평가 상태가 더해진다. [ERD quality_issue]
- **단계·다음에 할 일**: 저장하지 않고 이슈·평가·조치 요청·로트 상태로 계산한다. [ERD batch 계산 값 "다음에 할 일·단계"]

## 4. 성공 기준

### 완료 확인
- **SC-001**: 관리기준 이탈 이슈에서 평가를 작성하면 근거(로트·측정값·기준·버전)가 자동으로 보이고, 필수 칸이 비면 제출되지 않으며, 제출하면 "검토 요청"과 업무 이력이 보인다. (관련: FR-001)
- **SC-002**: QA 관리자가 보완 요청(사유) → 요청자가 고쳐 다시 제출 → 승인하는 흐름이 끝까지 되고, 각 단계가 업무 이력에 남는다. 승인 창에 "사용·출하 승인이 아닙니다"가 보인다. (관련: FR-002, FR-003, FR-005)
- **SC-003**: 평가 없이·미승인으로 닫기는 막히고 이유가 보인다. 관리기준 이탈은 평가 승인만으로, 규격 이탈은 평가 승인 + 완료된 조치로 닫힌다. (관련: FR-004)
- **SC-004**: 규격 이탈 이슈의 평가가 승인돼도 조치가 끝나지 않았거나 마지막 값이 규격 이탈이면 내부 출하 검토의 출하 가능이 막힌다(화면·데이터베이스). (관련: FR-005)
- **SC-005**: 이슈 상세 단계 표시줄과 다음에 할 일이 규칙 9가지대로 바뀌고, 로트 상세 위쪽에 종류별 열린 이슈 수·평가 상태·다음에 할 일이 보인다. (관련: FR-006, FR-007)
- **SC-006**: 검토 요청 평가가 QA 관리자 대시보드·승인 대기에, 보완 요청·반려된 평가가 요청자 첫 화면에 보인다. (관련: FR-008)
- **SC-007**: QA 관리자가 아닌 역할은 검토할 수 없고, 요청자가 아닌 사람은 다시 제출할 수 없으며, 이슈당 평가는 하나다(화면·데이터베이스). 기존 시험(함수 76, DB 001~004)이 그대로 통과한다(닫기 조건이 바뀐 사례는 새 규칙으로 고침). (관련: FR-001~004)
