## 1. 요약
가상 백신 제조사의 QA 관리자가 시험·생산·평가서·메일·엑셀을 따로 뒤지지 않고, 로트 하나의 품질 이탈이 이탈 근거 → 품질 영향 평가 → 후속 조치 → 이슈 종료까지 어디까지 처리됐고 누가 무엇을 근거로 승인했는지를 한 화면에서 보고, 1분 안에 회사 내부 출하 검토를 하게 하는 웹 앱이다. 시험 결과와 공정 조건은 시험 규격·사내 관리기준으로 세 단계 판정하고, 규격 이탈만 자동 보류한다. 이 앱은 국가출하승인을 하지 않으며 모든 기준·로트는 교육용 가상 자료다. 2026-10-27 발표에서 청중이 구글 계정으로 직접 들어와 써 볼 수 있어야 한다.

## 2. 배경과 문제
모든 근거는 가상 시나리오에 기반한 **가설**이다(8번). v0.4에서는 AI 페르소나 5명 인터뷰(`docs/interview.md`)로 확인된 것을 **[인터뷰 N/5]**로 표시하고, 확인되지 않은 것은 **[가설 유지]**로 둔다. 인터뷰의 숫자와 에피소드는 AI가 설정한 값이므로 사실이 아니라 가정이다.
1. **출하 검토 직전의 확인이 오래 걸리고 놓치기 쉽다.** 시험·생산 기록, 평가서, 메일, 엑셀을 따로 뒤져야 한다. 인터뷰에서 확인 시간은 **약 30분이 아니라 환경에 따라 15분(MES·LIMS·eQMS를 갖춘 대형사)~3~4시간(종이·엑셀 중소사)** 이었다. 열린 일탈·변경 건을 **서명 직전에야 알게 되는 일이 연 1~3회** 있었다(놓칠 뻔함, 사고는 없음). 감정 최저점은 "놓친 이탈이나 승인 안 된 평가가 있을까" 하는 불안이다. [인터뷰 4/5: 여러 곳을 오가며 확인, 3/5: 서명 직전에 열린 건 발견] (CUJ-01 6단계 As-Is)
2. **이탈이 사람 손으로 전달된다.** 시험 담당자가 메일·전화로 알려야 해서 누락·지연이 생긴다. 반대로 경미한 이탈까지 모두 멈추면 출하가 불필요하게 막힌다. **[가설 유지]** 이탈 값을 전달하다 누락·지연된 사례는 인터뷰 0/5였고, 사내 경보 범위 때문에 로트 전체가 묶여 하루 밀린 사례만 1/5였다. (CUJ-01 2단계, CUJ-02 3단계)
3. **이탈 원인·품질 영향 평가·승인 근거가 흩어져 있다.** 평가서는 워드로 메일에 첨부되고, 어떤 기준으로 판정했는지 나중에 재현하기 어렵다. 인터뷰에서 확인된 것: 일탈·평가 양식에 시험값과 기준을 **옮겨 적다 반려·보완이 오감 [인터뷰 2/5]**, 점검·실사 때 **승인 근거를 메일·결재함·폴더에서 뒤짐 [인터뷰 2/5, 최대 하루]**. 평가 승인이 출하 승인처럼 오해될 수 있다는 것은 **[인터뷰 1/5, 본인은 "자주·크게 부담되지 않았다"]**. (CUJ-01 3~4단계)
4. **로트의 내부 품질 상태를 묻는 쪽이 QA에게 물어봐야 안다.** 보류·검토 중 로트와 조치 지연을 직접 볼 곳이 없다. 인터뷰에서 상태를 묻는 쪽은 인허가·공급 담당자가 아니라 **영업·생산·위탁사**였다 [인터뷰 4/5, 하루 4~5번~주 5~6건~월 6~8건, 단위가 달라 비교 불가]. 인허가·공급 담당자가 QA에 물어본다는 것은 **[가설 유지, 인터뷰 대상 없음]**이다. (문제정의 v2 네 칸 "누가")
5. **(신규) 종결·진행 상태가 서로에게 안 전달돼 기다리고 묻는다.** 한서윤(QA)은 "QC가 LIMS에서만 완료 처리하고 eQMS 종결을 안 한다"고 하고, 강동혁(QC)은 "QA 종료 서명이 월요일까지 안 오는데 독촉은 QC로 온다"고 한다. 같은 구조가 반대 방향으로 나타난다. [인터뷰 5/5]
6. **(신규) 기존 기록·대장·공유표 시도가 상대의 입력·갱신 협조 부족으로 실패한다.** 오태민의 통합 엑셀 대장(QC가 입력 안 해 3주 만에 혼자 사용), 문지아의 주간 현황표(갱신이 늦어 아무도 안 믿음), 강동혁의 반납 대장(생산이 기입 안 함). 한서윤은 시스템 연동 요청이 밸리데이션 비용으로 2년째 보류, 서하은은 공통 양식 제안이 위탁사 고집으로 무산. [인터뷰 5/5] **이 앱도 QC·생산이 입력해야 돌아가므로 같은 위험을 진다(8번).**

### 2-1. 문제 문장 (인터뷰 후, 최종)
> **QA 관리자(출하 판정 담당)**는 **로트 출하 서명 직전에 상태를 확인할 때**, 열린 일탈·변경 건과 시험·기록 상태가 시스템·엑셀·폴더에 나뉘어 있고 사람이 따로 입력·전달해야 최신이 되기 때문에 **로트당 15분~3~4시간을 들여 맞춰 보고, 서명 직전에야 열린 건을 알게 되는 일을 연 1~3회 겪는다(판정이 멈춤, 놓칠 뻔함).** 지금은 **시스템별 개별 조회 + 개인 엑셀·대장 + 담당자 메신저·메일 문의**로 버틴다.

- 근거: `docs/interview.md` 8절 후보 1(패턴 P1 4명, P2 3명, P7 5명). 인터뷰 전 문장과 바뀐 점은 같은 문서 9절.
- 한계: 모든 숫자는 AI 페르소나 설정값이다(가정, `docs/interview.md` 10절 G1·G2). 손해는 시간과 지연뿐이고 돈은 0명, 실제 오출하·사고는 0건이다.

### 2-2. 5 Whys (같은 문제를 세 방향에서 세 번)
`[인터뷰]`는 `docs/interviews/` 원문에서 확인한 것, `[가설]`은 팀의 추론이다.

**① 시간이 왜 드나**
1. 왜 로트 하나 확인에 시간이 드나? → MES·LIMS·eQMS를 따로 열고 엑셀·폴더까지 오간다. `[인터뷰]` 4명
2. 왜 따로 여나? → 시스템이 서로 연동되지 않는다. `[인터뷰]` 한서윤
3. 왜 연동하지 않나? → 밸리데이션 재수행 비용 때문에 2년째 보류다. `[인터뷰]` 한서윤
4. 왜 사람이 맞추는 쪽을 택하나? → 개인 엑셀 확인표로 혼자 버티는 게 더 싸다. `[인터뷰]` 한서윤
5. 왜 계속되나? → 시스템은 두고 한 로트의 상태만 한곳에 모아 보여 주는 중간 수단이 없다. `[가설]`

**② 왜 서명 직전에야 아나**
1. 왜 직전에야 아나? → 보는 화면에 그 건이 반영돼 있지 않다. `[인터뷰]` 한서윤, 문지아
2. 왜 반영이 안 됐나? → 열린 건은 eQMS에만 있고 확인하는 화면은 다른 곳이다. `[인터뷰]` 한서윤, 문지아
3. 왜 알려 주는 사람이 없었나? → 알림이 변경 담당자의 메일이나 다른 부서 회의에서 우연히 들은 것뿐이다. `[인터뷰]` 한서윤, 문지아
4. 왜 정해진 통지 경로가 없나? → 일탈·변경 종결은 담당 부서 일이고 출하 검토는 QA 일이라 둘을 잇는 단계가 없다. `[가설]`
5. 왜 서명 단계가 막지 못하나? → 열린 건 확인이 서명 절차에 걸려 있지 않고 사람의 점검에 달려 있다. `[가설]`

**③ 해 본 시도가 왜 실패했나**
1. 왜 대장·공유표를 만들어도 안 줄었나? → 5명 모두 시도했고 실패했다. `[인터뷰]` 5명
2. 왜 실패했나? → 상대가 입력·갱신을 안 해서 한쪽만 쓰거나 아무도 믿지 않게 됐다. `[인터뷰]` 오태민, 문지아, 강동혁
3. 왜 입력을 안 하나? → 약속에만 기대는 구조다. `[인터뷰]` 강동혁, 오태민
4. 왜 약속이 안 지켜지나? → 입력하지 않아도 자기 일은 끝난 것으로 보인다. `[인터뷰]` 한서윤, 강동혁
5. 왜 그렇게 보이나? → 일을 끝내는 행동(시험 완료, 서명)과 상태를 갱신하는 행동이 따로라 갱신이 빠진다. `[가설]`

**세 줄을 합친 뿌리:** 일을 하면 상태가 한곳에 저절로 쌓이는 구조가 아니라, 사람이 따로 입력·전달해야 최신이 된다. 우리 앱은 일하는 행동이 곧 기록이 되게 한다(업무 이력 자동 기록 FR-16, 열린 이슈가 출하를 막는 규칙 FR-15, 로트 상세에서 열린 이슈 수 먼저 보이기). `[가설]` 칸은 실제 사람 한 명에게 같은 질문지로 확인한다.

## 3. 목표와 성공 지표

- 발표에서는 이 목표를 청중이 직접 로그인해 이탈 → 영향 평가 → 조치 → 내부 출하 검토 흐름을 끝까지 따라가 보이는 것으로 확인한다 (2026-10-27 발표).

## 5. 가치 제안
### QA 관리자
- **누가:** 로트의 내부 출하 검토 책임이 있는 QA 관리자
- **왜:** 로트를 출하해도 되는지 판단해야 하는데, 이탈 근거·영향 평가·조치·승인 이력이 흩어져 있다
- **이전:** 시험·생산 기록, 평가서, 메일, 엑셀을 따로 뒤진다(로트당 15분~3~4시간, 인터뷰 AI 설정값 가정). 열린 건을 서명 직전에야 알게 되는 일이 연 1~3회 있어 놓칠까 불안하다
- **어떻게:** 로트 상세 한 화면에 열린 품질 이슈(종류별), 영향 평가·조치 상태, 판정 근거, 다음에 할 일, 업무 이력을 모은다. 열린 이슈가 있으면 출하 가능을 막고, 영향 평가 승인만으로는 출하되지 않게 한다
- **이후:** 1분 안에 검토한다. 누가 언제 어떤 기준(버전)으로 무엇을 승인했는지 언제든 다시 확인할 수 있다
- **대안:** 엑셀 공유 시트. 이탈을 자동으로 감지하지 못하고, 판정 근거를 남기지 못하고, 승인 권한도 막지 못한다. 갱신이 사람 손에 달려, 상대가 입력하지 않으면 아무도 믿지 않게 된다 (인터뷰 3/5가 대장·현황표를 만들었다가 실패함)
> 로트 하나만 열면 이탈 근거부터 승인까지 다 보이고, 끝나지 않은 이탈이 있으면 실수로 출하할 수 없다.

### QC 시험 담당자
- **누가:** 로트 시험값을 입력하고 영향 평가를 쓰는 QC 시험 담당자
- **왜:** 이탈을 빠뜨리지 않고 알리고, 영향 평가와 재시험까지 이어 가야 한다
- **이전:** 기준서와 기록지를 눈으로 비교하고, 워드 평가서를 메일로 보낸다
- **어떻게:** 시험 규격·사내 관리기준을 입력 칸 옆에 보여 주고, 저장 즉시 세 단계 판정해 품질 이슈를 연다. 영향 평가에는 로트·측정값·기준이 자동으로 들어간다
- **이후:** "알렸나?", "근거를 옮겨 적었나?"를 걱정하지 않는다
- **대안:** 메일과 워드. 근거 누락을 막지 못한다
> 시험값만 넣으면 판정과 보고가 끝나고, 평가서는 이슈 안에서 쓴다.

### 생산 담당자
- **누가:** 공정 조건을 기록하는 생산 담당자
- **왜:** 공정이 규격을 벗어나면 로트를 바로 멈추고 점검을 요청해야 한다
- **이전:** 보고서를 써서 전달한다. 바쁘면 늦어진다
- **어떻게:** 공정 조건을 저장하면 세 단계 판정하고, 규격 이탈이면 로트를 자동 보류한다. 설비 점검 요청까지 한 화면에서 끝낸다
- **이후:** 문제 로트가 내부 출하 검토 대상에 섞이지 않는다
- **대안:** 구두 보고와 종이 기록. 이력이 남지 않는다
> 공정 조건만 넣으면 문제 로트가 알아서 멈춘다.

### 인허가·공급 담당자 (선택)
- **누가:** 로트의 품질 상태를 알아야 하는 인허가·공급 담당자
- **왜:** 제출 준비와 공급 일정을 세우려면 보류·검토 중 로트와 지연을 알아야 한다
- **이전:** QA에 물어본다
- **어떻게:** 로그인한 누구나 읽기만 하는 품질 현황 화면(로트별 상태, 지연, 계산된 문서 준비 상태)
- **이후:** 묻지 않고 확인한다. 앱은 규제기관 판단을 대신하지 않는다
- **대안:** 메신저 문의
> 물어보지 않고 로트의 내부 품질 상태를 본다.

## 6. 핵심 사용자 여정 (CUJ)
여정 지도와 단계별 감정은 `docs/journeys/`에 있다. 여기에는 결정에 필요한 것만 적는다.

### CUJ-01: 백신 로트 시험 이탈부터 내부 출하 검토까지
- 사용자 그룹 / 목표: QA 관리자(+QC 시험 담당자) / 근거를 확인하고 1분 안에 내부 출하 검토
- 유형: OEC 기반
- 사용자 스토리: "QA 관리자인 나는 로트를 안심하고 출하하기 위해, 그 로트의 이탈 근거·영향 평가·조치·승인 이력을 한 화면에서 보기를 원한다."
- 시나리오:
  1. 품질시험 홈 (`HM_020000_PG`) → 로트 상세 → 시험값 입력 (`BT_010206_MD`) — 시험 규격·사내 관리기준을 보며 측정값 저장
  2. **[MOT]** 시험 결과 탭 (`BT_010202_TB`) — 세 단계 판정. 관리기준 이탈이면 이슈만, 규격 이탈이면 이슈와 자동 보류 (감정 -1)
  3. 품질 이슈 상세 (`QI_010100_PG`) → 품질 영향 평가 작성 (`QI_010105_MD`)
  4. 승인 대기 (`AD_010000_PG`) → 품질 영향 평가 검토 (`QI_010106_MD`) / 조치 요청 등록·승인 (`QI_010101_MD`, `QI_010102_MD`)
     - 반려·보완 요청이면 → 사유와 함께 요청자에게 되돌림, 요청자가 고쳐 다시 제출
  5. 조치 결과 입력 (`QI_010104_MD`) → 이슈 닫기
     - 또 이탈이면 → 같은 이슈에 결과가 붙고 다른 조치 요청
  6. **[MOT]** 로트 상세 (`BT_010200_PG`) → 내부 출하 검토 (`BT_010208_MD`) — 열린 이슈 0건과 근거 확인 후 결정 (감정 +2)
- 성공 기준: QA 관리자가 로트 상세 진입 후 1분 안에 내부 출하 검토
- 에러·복구: E1 저장 실패, E2 권한 없음, E3 반려 후 재제출, E6 관리기준 이탈, E7 보완 요청, E8 특채 시도 차단

### CUJ-02: 공정 이탈부터 로트 보류·조치까지
- 사용자 그룹 / 목표: 생산 담당자 / 문제 로트를 바로 멈추고 점검 요청
- 유형: OEC 기반
- 사용자 스토리: "생산 담당자인 나는 문제 로트가 출하로 넘어가지 않게 하기 위해, 공정 조건을 저장하는 즉시 규격 이탈 로트가 보류되기를 원한다."
- 시나리오:
  1. 제조공정 홈 (`HM_030000_PG`) → 로트 상세 → 공정 조건 입력 (`BT_010205_MD`)
  2. **[MOT]** 공정 조건 탭 (`BT_010201_TB`) — 이탈이면 품질 이슈(공정) 1개, 규격 이탈이면 로트 자동 보류
  3. 조치 요청 등록 (`QI_010101_MD`, 기본값 설비 점검) → 이후 CUJ-01 3~6단계
- 성공 기준: 규격 이탈 저장과 동시에 보류(0초)
- 에러·복구: E1, E2, E6과 같음

### CUJ-03: 첫 로그인부터 역할을 받아 내 첫 화면에 들어가기까지
- 사용자 그룹 / 목표: 처음 로그인한 사람 + QA 관리자 / 가입 없이 들어가 내 일이 있는 화면으로
- 유형: High-Traffic (발표 때 청중 전원이 거침)
- 사용자 스토리: "처음 온 사용자인 나는 헤매지 않고 업무를 시작하기 위해, 구글 계정으로 들어가 내가 할 수 있는 일을 바로 알기를 원한다."
- 시나리오:
  1. 로그인 (`MB_000000_PG`) — 구글로 로그인
  2. **[MOT]** 로트 목록 (`BT_010000_PG`) — 열람자로 도착, 읽기 전용 이유와 할 일 안내 (감정 -1)
  3. 사용자·역할 (`AD_020000_PG`) — QA 관리자가 역할 지정
  4. 역할별 첫 화면 (`HM_010000_PG`, `HM_020000_PG`, `HM_030000_PG`) — 다음 화면 이동부터 적용
- 성공 기준: 다시 로그인하지 않고 역할이 적용됨
- 에러·복구: 로그인 실패 → 로그인 화면에 안내 후 재시도

- 바꾸는 것: 사용자 역할 지정, 조치 요청·영향 평가 승인·반려·보완 요청, 시험 규격·관리기준, 내부 출하 검토(출하 가능·폐기), 직접 보류.

**요청과 반응 흐름 (하나)**
1. QC 시험 담당자가 시험값을 저장한다 (요청).
2. 값이 규격을 벗어나면 앱이 품질 이슈를 자동으로 열고 로트를 자동 보류한다. 관리기준만 벗어나면 이슈만 열고 보류하지 않는다 (반응, FR-08·29).
3. 받는 사람에게 슬랙 개인 메시지와 앱 안 알림이 간다 (반응, FR-41·42).
4. 담당자가 영향 평가를 쓰고 조치를 요청한다 (요청, FR-30·12).
5. QA 관리자 승인 대기에 올라오고, QA 관리자가 승인·반려·보완 요청한다 (반응, FR-13·31).
6. 배정된 담당자가 조치 결과를 넣고 이슈를 닫는다 (FR-14·32).
7. 열린 이슈가 없으면 QA 관리자가 내부 출하 검토를 한다. 모든 단계는 업무 이력에 남는다 (FR-15·16).

**DB·배포를 고른 이유**
- DB는 Supabase: 업무 이력·사용 기록을 관리 화면에서 모아 보려면 모두가 같은 자료를 봐야 하고, "누가 승인했나"를 믿으려면 진짜 로그인과 DB 쪽 권한이 필요하다 (ADR 0002). 브라우저에만 저장하는 방식과 이름만 고르는 로그인은 검토 후 버렸다.
- 배포는 Vercel: 청중이 인터넷 주소로 직접 들어오는 발표 방식에 맞고, 서울 지역 함수에서 공공데이터 호출이 막히지 않음을 2026-10-22에 확인했다 (ADR 0001). 미리 받아 둔 스냅샷과 PC 프록시는 검토 후 버렸다.

## 8. 결정·제약·가정
**주요 결정**
- 빌드 없는 HTML/JS를 유지한다. (CLAUDE.md 스택)
- 모든 자료는 Supabase, 로그인은 구글, 권한은 데이터베이스 규칙(RLS)과 함수로 막는다. (ADR 0002)
- 공공데이터는 Vercel 함수가 인증키를 붙여 대신 부른다. 함수 지역은 서울. (ADR 0001)
- 핵심 흐름(CUJ-01~03)은 공공데이터 없이도 끝까지 동작해야 한다.
- PharmaFlow Bio 전환 결정 D1~D14 (`docs/전환-영향분석-PharmaFlow-Bio.md`): 화면 이름만 로트(D3), 새 역할 없음(D4), 스냅샷 + 기준 버전(D5), 관리기준 이탈은 보류 없이 이슈·출하는 막음(D6), 영향 평가는 이슈당 하나·후속 조치는 기존 조치 요청(D7), 닫기 조건(D8), 체크리스트는 계산(D9), 마지막 정상 조회는 브라우저에만(D10), 개발은 자료를 지우지 않음(D11), 공급사 규칙(D12), MSDS 링크(D13)
- 브랜치·PR로 작업한다(D2, CLAUDE.md).

**종속성 (외부연동)**
- Supabase (자료, 구글 로그인), Google Cloud OAuth 클라이언트, Vercel (배포·함수)
- 공공데이터포털: 의약품 제품 허가정보(15095677, 실시간, 10,000건/일), 의약품 회수·판매중지(15059114, 실시간, 10,000건/일). 백신은 허가정보에서 검색됨(2026-10-22: "백신" 164건, 품목 구분 [06310]백신류). 회수 공지에서 "백신" 이름 검색은 0건. MSDS(15157612)는 키 미등록

**개인정보**
- 구글 계정의 이름·이메일을 저장한다. 이메일은 사용자·역할 화면에서 QA 관리자만 본다. 사용 기록에는 사용자 ID만 남긴다.
- 교육용 가상 자료만 쓴다. 실제 회사·로트 자료는 넣지 않는다.

**가정과 미결 질문**
| 가정·질문 | 확인 방법 | 담당 |
|---|---|---|

## 9. 출시 계획
- **1차 범위 (2026-10-27 발표):** Must FR-01~17, FR-27~36, FR-40~42 + Should FR-18~21·23~25. 선택은 FR-37 → FR-38 → FR-39 순서로 하고, 시간이 모자라면 뒤에서부터 뺀다.
- **처리 안 한 여정 페인포인트:** 없음. MOT와 감정 -1 구간이 FR-02, FR-08, FR-09, FR-15, FR-27, FR-29, FR-30, FR-33, FR-36으로 이어진다.
- **이후 범위:** 결과 비교(FR-26), MSDS 앱 안 검색·취급점검 화면(FR-22), KPI 차트, 매일 요약·기한 지남 다시 알림, AI 품질 브리핑(spec 010 후보), 휴대폰 전용 화면 다듬기.
- **하지 않을 것:**
  - 실제 회사·로트 자료 사용, 실제 의약품 규격을 법정 기준처럼 표시하기
  - 규격 이탈 로트를 QA 버튼 하나로 특채 사용·출하 승인하기
  - 국가출하승인·허가 여부·법적 적합 여부를 결정하거나 보증하기
  - 공급사를 자동으로 부적격 처리하기
  - 인허가 시스템·영업관리 시스템 만들기
  - LIMS의 시험 건 종료 서명 대체 (인터뷰에서 QC 1명이 꼽음. 같은 답변의 샘플 수령·반납·위치 추적은 spec 008 검체 인계로 이미 범위 안)
  - 메일·문자·푸시 알림 발송 (슬랙 개인 메시지 알림만 spec 009로 허용, 2026-10-26 사용자 결정, ADR 0003)
  - 결재 시스템 연동, 전자서명 (GMP·21 CFR Part 11 수준의 규정 준수)
  - 아이디·비밀번호 회원가입 (구글 로그인만)
  - 공공데이터를 우리 데이터베이스에 대량으로 복사해 두기
