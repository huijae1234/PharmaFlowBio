## 3. DB 스키마 변경안 (모두 "더하기", 기존 자료는 지우거나 바꾸지 않음)

### 3-1. 필수 (Phase 2·4)
| 대상 | 변경 | 기존 자료 영향 |
|---|---|---|
| `specification` | `alert_min_value`, `alert_max_value` 추가 (비워 둘 수 있음, 관리기준). `version int default 1` 추가 (저장할 때마다 +1) | 기존 기준은 관리기준 비어 있음 → 판정이 지금과 같음 |
| `measurement` | `applied_alert_min_value`, `applied_alert_max_value`, `applied_spec_version` 추가 (판정에 쓴 그때 값) | 기존 행은 비어 있음/버전 1로 채움 |
| `measurement_result` enum | `out_of_alert`(관리기준 이탈) 값 추가 | 기존 `pass`·`out_of_spec` 그대로. **enum 추가는 그 값을 쓰는 함수와 다른 마이그레이션으로 나눔** |
| `quality_issue` | `kind` 추가: `spec`(규격 이탈, 보류) / `alert`(관리기준 이탈, 보류 없음). 기본값 `spec` | 기존 이슈는 모두 `spec` |
| 신규 `deviation_review` (품질 영향 평가) | 이슈 1건당 1건(최신). 칸: quality_issue_id, 추정 원인, 이탈 내용, 품질 영향 평가, 제안 후속 조치, 근거, 상태(작성 중·검토 요청·승인·반려·보완 요청), 요청자·요청 시각, 검토자·검토 시각, 승인·반려·보완 사유, 처리 결과. 로트·발생 일시·시험 항목·측정값·적용 기준·버전은 **저장하지 않고 이슈·측정값에서 읽음** (중복 저장 방지) | 신규 |
