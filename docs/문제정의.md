# 문제 정의: 백신 제조 로트의 품질 이탈을 출하 검토 전에 한곳에서 추적하기 (PharmaFlow Bio)

- 버전: v2.1 (2026-10-28, v2는 승인 2026-10-22). v1(일반 의약품 배치 출하 판정)에서 주제를 바꿈 → 맨 아래 변경 기록
- 근거: 사용자 요청 "PharmaFlow Bio 프로젝트 전환 및 기능 확장 요청"(2026-10-22) 3~7절, `docs/전환-영향분석-PharmaFlow-Bio.md`(D1~D14 승인)

모든 회사·제조 로트·시험 결과·공정 조건·공급사·시험 규격·사내 관리기준은 **교육용 가상 자료**다. 식약처 허가정보·회수·판매중지 정보만 실제 공개 자료를 쓴다. 용어는 `GLOSSARY.md`를 따른다.

> 아래 걸림돌(C)은 이 프로젝트에서 **검증할 문제 가설**이다. 실제 백신 업계 전체의 확정된 사실로 쓰지 않는다.

## SCQA
- **상황(S):** 가상 백신 제조사에서 QC 시험 담당자는 제조 로트의 시험 결과를, 생산 담당자는 공정 조건을 기록한다. 결과가 시험 규격이나 사내 관리기준을 벗어나면 품질 이슈가 생기고, 담당자가 품질 영향 평가와 후속 조치(재시험·설비 점검·원료 확인 등)를 진행한다. QA 관리자는 이를 검토·승인한 뒤 회사 내부의 출하 검토를 한다.
- **걸림돌(C, 가설):** 이탈 원인, 품질 영향 평가, 후속 조치, 승인 이력이 시험 기록·생산 기록·메일·엑셀에 흩어져 있어서, 생산·품질·인허가 담당자가 한 로트의 이탈이 어디까지 처리됐는지와 누가 무엇을 근거로 승인했는지를 일관되게 확인하기 어렵다. 출하 검토 직전에 놓치기 쉽다.
- **질문(Q):** 이탈 발생부터 품질 영향 평가·후속 조치·이슈 종료·내부 출하 검토까지를 여러 화면과 기록을 뒤지지 않고 한 로트 기준으로 추적하려면 어떻게 해야 하는가?
- **지금의 답(A):** 로트에 시험 결과를 넣으면 시험 규격과 사내 관리기준으로 **세 단계 판정**(정상·관리기준 이탈·규격 이탈)을 하고, 이탈이면 품질 이슈를 연다(규격 이탈은 자동 보류). 그 이슈가 품질 영향 평가 → QA 검토 → 후속 조치 → 이슈 종료 → 내부 출하 검토까지 상태와 업무 이력으로 추적된다(구글 로그인과 역할별 권한 포함).

## 네 칸
| 누가 | 언제 | 무엇이 | 얼마나 |
|---|---|---|---|
| QA 관리자(출하 판정 담당) (보조: QC 시험 담당자, 생산 담당자 / 읽기만: 인허가·공급 담당자) | 로트 출하 서명 직전에 상태를 확인할 때, 그리고 시험·공정 이탈이 생겼을 때 | 열린 일탈·변경 건과 시험·기록 상태가 시스템·엑셀·폴더에 나뉘어 있고 사람이 따로 입력·전달해야 최신이 되어, 한 로트의 처리 상태와 판단 근거를 한 번에 볼 수 없다. 서명 직전에야 열린 건을 알게 되는 일이 연 1~3회 있다 | 로트 하나 확인에 15분(전자 시스템 보유 대형사)~3~4시간(종이·엑셀 중소사) → 1분 안. 처리 상태를 묻는 연락은 하루 4~5번~월 6~8건(단위가 달라 합산 안 함) → 로트 상세에서 먼저 확인 (모두 AI 페르소나 설정값, 가정. `docs/interview.md` 4·9절) |

## 확인할 것 하나
로트 상세와 품질 이슈 상세에서, 이탈 발생부터 조치 완료까지의 판정 근거(적용 기준과 버전)·영향 평가·승인자·업무 이력·다음에 할 일을 다른 화면으로 옮겨 다니지 않고 확인하고, QA 관리자가 1분 안에 내부 출하 검토를 할 수 있는가.

## 정한 범위와 제약
- **사용자와 권한:** 구글 로그인. 처음 로그인하면 열람자이고 QA 관리자가 역할(QC 시험 담당자, 생산 담당자, QA 관리자)을 지정한다. 권한은 데이터베이스 규칙으로도 막는다. 인허가·공급 담당자용 새 역할은 만들지 않고, 필요한 정보는 로그인한 모든 사람이 읽기만 하는 화면으로 준다 (ADR 0002, 전환 D4).
- **판정 세 단계:** 정상(시험 규격과 사내 관리기준 모두 충족) / 관리기준 이탈(시험 규격은 충족, 사내 관리기준만 벗어남 → 품질 이슈를 열고 영향 검토, 자동 보류 없음) / 규격 이탈(시험 규격을 벗어남 → 품질 이슈와 자동 보류, 조사와 처분 없이 사용·출하 불가). 측정 당시 적용한 기준과 버전을 함께 남겨 나중에 판정 근거를 재현한다 (전환 D5·D6).
- **품질 이탈 및 예외처리 검토:** 담당자가 품질 영향 평가(이탈 내용·추정 원인·영향·제안 조치·근거)를 작성하고 QA 관리자가 승인·반려·보완 요청한다. QA 검토 승인은 출하 승인이 아니다. 규격 이탈 로트를 버튼 하나로 특채 사용·출하 승인하는 기능은 만들지 않는다 (전환 D7·D8).
- **내부 출하 검토:** QA 관리자만 출하 가능 또는 폐기로 정한다. 열린 품질 이슈가 있거나 시험이 끝나지 않았으면 출하 가능을 막는다. 이 앱의 판단은 회사 내부 검토이며 국가출하승인이나 법적 적합 여부를 결정하거나 보증하지 않는다.
- **로트 상태:** 생산 중 → 시험 중 → 보류 → 출하 가능 / 폐기.
- **재시험이 또 이탈이면:** 같은 품질 이슈에 결과를 붙이고, 이슈는 열린 채 다른 조치를 요청한다.
- **반려·보완 요청:** 사유가 필수이고, 요청자가 고쳐 다시 제출할 수 있다. 모두 업무 이력에 남는다.
- **기록:** 업무 이력(누가 언제 무엇을 했나)과 사용 기록(로그인·화면 이동·검색어·공공데이터 호출 결과)을 남긴다. 사용 기록에는 이메일 대신 사용자 ID만 남긴다.
- **공개 정보:** 백신 제품 허가정보와 회수·판매중지 정보를 출처·조회 시각과 함께 보여 준다. 허가정보가 로트별 법정 시험 규격을 주지는 않는다. MSDS는 공단 사이트 링크만 둔다 (전환 D13). 공공데이터는 Vercel 함수가 대신 실시간 호출하고 DB에 대량 복사하지 않는다 (ADR 0001).
- **선택 확장:** 공급사·원료 로트별 반복 이탈 감지(교육용 가상 규칙으로 검토 요청만 만들고 자동 부적격 처리는 하지 않음), 인허가·공급 담당자용 읽기 전용 품질 현황 조회.
- **배포:** Vercel. 청중이 인터넷 주소로 직접 들어와 본다. 관리 메뉴에 "예시 자료로 되돌리기"(QA 관리자가 직접 누를 때만)를 둔다. 개발·마이그레이션은 기존 자료를 지우지 않는다 (전환 D11).
- **기한:** 2026-10-27(화) 발표. 혼자서도 끝낼 수 있는 범위로 한다.
- **우선순위:** 꼭 = 기존 요청·승인·처리·출하 검토(완료) → 백신 로트 시나리오·세 단계 판정 → 품질 영향 평가 기본 → 백신 허가정보·회수 정보 출처 표시. 선택 = 품질 영향 평가 상세 → 인허가·공급 조회 → 공급사 반복 이탈 감지. 시간이 모자라면 선택을 뒤에서부터 뺀다.
