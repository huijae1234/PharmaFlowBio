# PharmaFlow 리뷰

1. 먼저 기본 `/code-review`를 바뀐 파일에 돌린다. 비밀 키·로그인·권한·배포가 건드려졌으면 `/security-review`도 돌린다.
2. 아래 여섯 가지를 **바뀐 파일에서** 확인한다. 각각 "통과 / 걸림 / 해당 없음"과 근거(파일:줄)를 적는다.

| 번호 | 확인 | 어떻게 본다 |
|---|---|---|
| 1 | **키가 화면 코드에 있나** | `src/`, `index.html`에 `service_role`·`sb_secret_`·`xox`·인증키 이름이 코드로 있으면 걸림. `src/config.js`에는 공개 키만. (`tests/architecture.test.js`가 자동으로 본다) |
| 2 | **/admin과 쓰기가 서버에서도 막히나** | 화면의 `canOpen`·버튼 표는 보이기만 정한다. 새 쓰기 함수에 `private.require_role`이 있는지, 새 표에 RLS가 켜져 있는지, `api/` 함수가 `verifyUser`로 로그인을 확인하는지 본다 |
| 3 | **층 방향** | `src/domain/`이 `ui`·`infrastructure`·`api`를 가져오면 걸림. 새 규칙은 domain에서 시작한다 (`tests/architecture.test.js`) |
| 4 | **같은 요청 두 번·동시 요청** | 상태를 바꾸는 새 DB 함수가 행을 잠그고 현재 상태를 확인하는지, "이미 …"·"다른 사람이 먼저 처리했습니다" 문구가 있는지 본다 |
| 5 | **화면 규칙과 DB 규칙이 같나** | 수량 한도·빈 값·범위 검사를 화면(`domain/`)과 DB 함수에 같은 값으로 넣었는지 본다 |
| 6 | **문서·시험 한 세트** | 새 규칙은 시험이 먼저. `node --test "tests/*.test.js"` 통과, 시험 개수를 적은 곳(README, CLAUDE.md, PRD, coverage)이 맞는지, 어긋나면 원문서를 먼저 고친다 |

3. 결과는 `review.md` 맨 위에 날짜, 대상, 여섯 줄 표로 더한다. 걸린 것은 고치기 전에 김희재에게 알린다.

## 이 스킬을 만든 이유
기본 코드 리뷰는 코드 안의 버그를 찾지만, 이 프로젝트에서 실제로 문제가 되는 것은 "화면에서는 막았지만 서버에서는 안 막은 것"과 "시험 개수·문서가 어긋나는 것"이었다. 그래서 위 여섯 가지를 더했다.
