# plan.md 템플릿과 칸별 작성 규칙

plan은 승인된 spec을 **어떻게** 만들지 정한다. spec의 FR·SC 번호를 그대로 가져와 쓰고, plan에서 새 요구사항을 만들지 않는다. spec에 없는 기능이 필요해 보이면 spec을 먼저 고친다.

## 칸별 규칙

### 0. 요약
- 한 단락: 이번 plan이 다루는 FR 범위, 기술 접근 한 줄, 단계 수.

### 1. 기술과 버전 — 무엇으로 만드나, 정확한 버전
- 표로 쓴다: 영역(화면, 로직, 저장, 시험 도구, 실행 환경, 배포), 선택, **정확한 버전**, 왜 골랐나, 버린 대안.
- 버전은 실제로 확인한 값만 쓴다: `package.json`·잠금 파일, CDN 주소의 버전, `node --version` 같은 명령 결과. "최신", "latest", `^1.2`처럼 범위로 쓰지 않는다. 확인하지 못했으면 `[확인 필요]`.
- 외부 라이브러리를 쓰지 않으면 "없음"이라고 명시한다. 그것도 결정이다.
- 실행 환경(지원 브라우저, OS, 사내 PC 조건)을 적는다.

### 2. 구조와 파일 — 폴더와 파일, 표 모양(ERD), 파일별 역할
- **폴더 트리:** 지금 있는 것과 이번에 새로 생기는 것을 구분한다(`(신규)`, `(수정)` 표시).
- **파일별 역할 표:** 파일, 하는 일, 담당 FR, 건드리면 안 되는 것.
- **자료 구조:** ERD(docs/ERD.md)에서 엔터티·필드를 가져온다. ERD가 없으면 spec 3절 핵심 자료로 임시 구조를 쓰고 "ERD 작성 필요"라고 표시한다. 저장하는 값과 화면에서 계산하는 값을 구분한다.
- **화면 연결:** IA 화면 ID → 파일·영역. IA가 없으면 "IA 작성 필요".
- 한 파일이 너무 많은 일을 하면 나눌 경계를 제안한다(예: 계산 로직과 화면 그리기 분리).

### 3. 단계별 접근 — 몇 단계로 나눠 만드나
- 표로 쓴다: 단계, 목표, 다룰 FR, 결과물, **끝 조건**(어떻게 확인하면 끝인가), 먼저 풀려야 할 질문.
- 각 단계는 끝난 뒤 혼자 확인·시연할 수 있는 조각이어야 한다. P1 요구사항부터.
- 첫 단계는 되도록 "지금 동작을 깨지 않고 구조만 정리 + 시험 붙이기"로 시작한다.
- **새 라이브러리 원칙:** 기본은 추가하지 않는다. 꼭 필요하면 "새 의존성 기록" 표에 이름·정확한 버전·이유·직접 만들 때의 비용·버린 대안을 쓰고, 사용자 승인을 받는다.
- 단계 안의 작업은 체크박스 목록으로 쪼갠다(한 작업 = 한 번에 확인 가능한 변경).

### 4. 테스트 전략 — 무엇으로 확인하나
- **요구사항 추적 표:** spec의 모든 FR과 SC가 한 번 이상 나와야 한다. 열: FR/SC, 확인 방법(함수 시험 / 화면 눌러 보기 / QA), 시험 이름 또는 QA 번호.
- **함수 시험:** 도구와 정확한 버전, 실행 명령, 시험할 함수, 사례(정상값, 경계값, 빈 값, 잘못된 값). spec 3절 경계·예외 상황을 모두 사례로 바꾼다.
- **화면 눌러 보기:** 여정(UJ)의 단계나 spec의 사용자 이야기를 따라 누르는 순서와 보여야 할 결과.
- **QA:** 항목과 결과는 같은 폴더의 `qa.md`(`harness-qa`)에 둔다. plan에는 추적 표에 C·H 번호만 적는다.
- **회귀 확인:** 지금 동작하는 기능 목록과 매 단계 끝에 다시 확인하는 방법.

### 5. 제약과 주의점
- **보안:** 비밀 키·토큰을 코드와 저장소에 두지 않는다. 화면(브라우저)에 들어가도 되는 키와 안 되는 키를 구분한다. 사용자가 입력한 글자를 HTML로 그릴 때 이스케이프한다.
- **성능:** 숫자로 쓴다(예: 항목 N개에서 화면 표시 1초 이내). 근거가 없으면 가정과 질문 번호.
- **호환성:** 지원 브라우저·기기.
- **지금 돌아가는 기능 깨지 않기:** 지켜야 할 기존 동작을 구체적으로 나열한다.
- **경계 3단:**
  - 항상 할 것: 에이전트가 묻지 않고 해도 되는 것
  - 먼저 물을 것: 승인이 필요한 것 (새 라이브러리, 자료 구조 변경, 파일 삭제 등)
  - 절대 하지 말 것: 제외 범위 구현, 비밀 키 커밋, 시험 삭제로 실패 숨기기 등
- **위험과 대응:** 일어날 수 있는 문제, 영향, 대응.

## plan 품질 점검표 (저장 후 스스로 확인, 문서에는 넣지 않음)
- [ ] 다섯 칸(1~5절)이 모두 있다
- [ ] spec의 모든 FR·SC가 4절 요구사항 추적 표에 있다 (`scripts/check_spec_plan.py`로 확인)
- [ ] plan에만 있고 spec에 없는 FR 번호가 없다
- [ ] 모든 버전이 정확한 값이거나 `[확인 필요]`다 ("latest", "최신", `^` 범위 없음)
- [ ] 새 라이브러리가 있으면 새 의존성 기록에 이유와 대안이 있다
- [ ] 단계마다 끝 조건이 확인 가능한 문장이다
- [ ] 회귀 확인에 지금 동작하는 기능이 구체적으로 적혀 있다
- [ ] 경계 3단(항상/먼저 물을 것/절대)이 있고, spec 제외 범위가 "절대 하지 말 것"에 반영됐다
