# spec.md 템플릿과 칸별 작성 규칙

spec은 **무엇을, 왜** 만드는지만 쓴다. **어떻게**(언어, 라이브러리, 파일, 함수 이름)는 plan.md에 쓴다.
읽는 사람은 기획자, 현업 담당자, 개발자(코딩 에이전트 포함) 모두다. 비개발자가 읽어도 이해되는 말로 쓴다.

## 칸별 규칙

### 1. 해결하려는 문제 — 이 기능이 없어서 지금 무엇이 막히나
- 지금 방식(As-Is)을 한두 줄로 쓰고, 그 방식에서 막히는 지점을 쓴다.
- 문제의 크기(시간, 빈도, 대수)가 있으면 숫자로 쓰고, 모르면 "확인 필요"와 질문 번호를 단다.
- 근거: Intent 1절, 문제정의 SCQA, 여정 As-Is·페인포인트.

### 2. 주요 사용자 — 누가, 어떤 장면에서 쓰나
- **사용자:** 역할로 쓴다(이름 X). 여정의 페르소나가 있으면 그 이름을 쓴다.
- **사용자 이야기:** 우선순위(P1, P2, P3) 순으로 쓴다. 각 이야기는 다음을 갖는다.
  - 장면: "{누가} {언제/어디서} {무엇을 하려고} 이 기능을 연다"
  - 왜 이 우선순위인가
  - **혼자 확인하는 방법:** 이 이야기만 만들어도 확인·시연할 수 있는 방법. P1만 만들어도 쓸모 있는 최소 기능(MVP)이 되어야 한다.
- 근거: 문제정의 네 칸 "누가·언제", 여정 단계, IA 화면 ID.

### 3. 핵심 기능과 요구사항 — 만들어야 할 것 목록 (번호)
- 요구사항은 `FR-001`부터 번호를 붙이고, 한 번 붙인 번호는 바꾸거나 다시 쓰지 않는다(삭제는 "삭제됨"으로 남김).
- 문장은 **"시스템은 ~해야 한다"** 또는 조건이 있으면 **"~일 때, 시스템은 ~해야 한다"**(EARS 형식)로 쓴다. 한 문장에 요구 하나.
- 각 요구사항에 붙일 것: 우선순위(P1/P2/P3, 사용자 이야기와 맞춤), 화면 ID(IA에 있으면), 출처.
- 각 요구사항 아래 **수용 기준**을 Given/When/Then(전제/행동/결과)으로 적는다. 결과는 눈이나 값으로 확인할 수 있어야 한다.
- **경계·예외 상황:** 빈 값, 경계값(딱 N일), 날짜 계산의 특이점, 잘못된 입력, 대량 자료를 따로 목록으로 쓴다.
- **핵심 자료:** 이 기능이 다루는 대상(엔터티)과 그 대상이 갖는 정보를 쓴다. 타입·테이블 이름은 쓰지 않는다(ERD·plan의 일).
- 근거: 요구서 수용 기준, PRD FR, CUJ의 MOT, 여정 명세의 성공 기준.

### 4. 성공 기준 — 무엇이 되면 "끝"인가, 눈으로 확인할 수 있게
- `SC-001`부터 번호를 붙인다. 기술과 무관하고, 숫자나 눈으로 확인할 수 있는 결과로 쓴다.
  - 좋음: "주문 목록 화면을 열면 배송 지연 주문이 정상 주문과 다른 표시로 보인다"
  - 나쁨: "정렬 함수가 잘 동작한다", "사용성이 좋다"
- 두 종류를 함께 둔다.
  - **완료 확인:** 시연 순서. "화면을 열고 → ~을 누르면 → ~이 보인다"
  - **효과 지표:** 문제가 얼마나 줄었는지(시간, 횟수). 현재값과 목표값을 모르면 "확인 필요"와 질문 번호.
- 근거: 요구서 "성공을 어떻게 셀까", PRD KPI, CUJ 단계별 지표.

### 5. 제외 범위 — 이번에 일부러 안 만드는 것
- 표로 쓴다: 무엇, 왜 뺐나, 언제 다시 보나(2차/보류/영영 안 함).
- 사용자가 당연히 있을 거라 기대할 만한 것을 특히 적는다. 코딩 에이전트가 "친절하게" 덧붙이는 것을 막는다.
- 근거: 요구서 "하지 않을 것", PRD 범위 밖, IA의 2차·보류 화면.

### 6. 확인 필요 사항 — 아직 못 정한 것
- 표로 쓴다: 번호, 질문, 막고 있는 요구사항(FR/SC), 답이 나오기 전 가정, 출처.
- 원문 문서의 질문 번호(요구서 Q4 등)를 그대로 쓴다. 새 질문만 이어지는 번호.
- **가정**을 반드시 적는다. 가정이 있으면 개발은 진행할 수 있고, 답이 나오면 가정만 바꾼다.
- 요구사항 본문에 `[확인 필요: Q번호]` 표시는 **최대 3개**까지만 둔다. 범위 > 보안·개인정보 > 사용자 경험 > 기술 세부 순으로 중요한 것만 남기고, 나머지는 가정으로 처리해 이 표에 둔다.

- 버전: v{0.1}
- 작성일 / 최종 갱신: {YYYY-MM-DD} / {YYYY-MM-DD}
- 근거 문서: {docs/Intent.md, docs/요구서/..., docs/IA.md, docs/journeys/..., docs/PRD.md, docs/ERD.md 중 있는 것}

## spec 품질 점검표 (저장 후 스스로 확인, 문서에는 넣지 않음)
- [ ] 여섯 칸이 모두 있고, 비어 있는 칸은 "확인 필요"와 이유가 있다
- [ ] 언어·라이브러리·파일·함수 이름 같은 구현 내용이 없다
- [ ] 모든 FR이 "시스템은 ~해야 한다" 한 문장이고, 수용 기준이 하나 이상 있다
- [ ] 모든 수용 기준과 SC가 눈이나 값으로 확인할 수 있다 ("잘", "빠르게", "편하게" 없음)
- [ ] P1 이야기만으로 쓸모 있는 최소 기능이 된다
- [ ] 경계·예외 상황이 있다 (빈 값, 경계값, 잘못된 입력)
- [ ] 제외 범위가 있다
- [ ] 본문의 `[확인 필요]` 표시가 3개 이하이고, 나머지 미정 사항은 6절에 가정과 함께 있다
- [ ] 모든 항목에 출처가 있고, 출처 문서·ID가 실제로 존재한다
